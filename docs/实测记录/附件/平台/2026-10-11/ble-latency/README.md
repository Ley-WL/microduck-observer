# 2026-10-11 蓝牙往返300ms排查

用户报告App蓝牙往返300多ms，要求检查原因。主板只读显示一加Ace2已连接，统一服务BLE ready。本轮没有发送任何GATT请求、绑定测试、动作或修改连接参数，仅sudo btmon被动抓取12秒。未停止/重启现有服务。

passive-headers.json只保存HCI/ATT头、长度、时间，不保存值/密文/身份或凭据；原始抓包仅内存处理。analysis.json按接收ATT Write Request划组，排除末尾不完整组并要求最后通知小于满片；29个完整请求均27通知，ATT片载荷总量6428～6458字节（含协议分片头，并非纯JSON长度）。主板HCI收到请求到首通知median31.143ms（20.936～53.929），到末通知median285.987ms（268.832～310.963），首末发送跨度median254.026ms（246.456～261.646）。HCI主机交给控制器的时间不等于手机接收时间，不能把首31ms全部说成Rust运算耗时或对空中连接间隔下结论。

代码路径：Rust ducklink_motion::status每个command复制完整control/15关节紧凑反馈/方向四元数/标定/系统资源；ducklink::receive封装加密并以最多244字节分片。通知循环每片await notify后固定sleep8ms，27片首末之间至少有26次等待（名义208ms，实际调度可更长），与被动观察的254ms跨度一致。App BleLink.exchange等待分片全部收齐才返回，MainActivity.pump的busy串行门等待完整回复，往返计时从worker内command开始到完整响应解密结束，不包括此前worker排队或UI渲染。

结论：整包状态27片与人为每片等待是当前300ms明显贡献项；这不是BLE必须300ms。仍未测纯小包往返/手机收包各阶段/实际空中连接间隔，不能承诺优化后具体毫秒数。App未主动请求高连接优先级也属可调查项，未证其当前贡献。

建议改进顺序：控制回复与低频完整诊断/标定分开；保留控制状态、故障、反馈保持与身份认证；通知使用发送接口背压取代固定8ms休眠并实测稳定性；再测高优先级连接的实际影响。此轮仅完成检查，未改代码/部署或用运动验证。手机已连接仅说明发现问题本次不再阻断，用户未明确反馈此前0/0恢复步骤。
