| FFmpeg软件MJPEG q:v5 | 2.8663s | 3.6836s | 28.663ms | 36.836ms |

VEPU中断0→100，软件编码后仍100；MPP退出0，ffprobe实际解码计数100帧、640×360 MJPEG。MPP内部统计编码466ms/100帧（214.21fps），与包含启动和IO的外部0.5074s口径不同。硬编码单独编码阶段CPU时间少约93%，不能据此声称整个摄像头服务CPU降低93%。MPP输出621200字节、软件204100字节，qfactor与q:v不是等价质量参数，未进行等码率/等画质比较；仅同输入可行性和资源短测。

结论：可用原生MPP替换软件JPEG编码，维持现有multipart MJPEG网页/img接口，无需先改H.264播放器。建议后续Rust摄像头worker管理原生MPP helper或FFI，采集NV12→图像校正/RGA→MPP JPEG→现有Rust发布，检测直接分流原始帧。RGA不自动等价替代现有白平衡/gamma LUT，需保留校正或另行验证ISP路径；不能直接删除校正导致偏绿恢复。也可使用带rkmpp的FFmpeg分支，但现有二进制不能只改编码器参数就启用。

本轮仅独立可行性验证，没有替换现役摄像头服务；设备节点仍root0600，测试以root运行，后续部署需最小访问权限而非全局chmod666。无Python编码服务（Python仅一次性编排/统计）。前端保持当前状态，最终15在线全卸力、idle、相机PID1082/1083保持。

## 2026-10-19 全链路耗时/CPU分析（最新纠正：RKNN调用不等于纯NPU）

用户要求分析全部步骤与CPU。本次未改运行策略，增加基准 `CLOCK_PROCESS_CPUTIME_ID` 分段CPU计时及可选 `RKNN_BENCH_PERF=1` 逐层诊断。耗时表来自关闭逐层诊断的5预热+100次同一360×640实拍、RGA路径；逐层诊断单独运行，不能把其数值混入正常速度表。

CPU-ms是进程所有线程实际使用CPU时间，不等于墙钟，不应把硬件等待计为CPU忙碌；微小差异来自采样与计时开销。进程无间隔循环占单核37.28%/69.95%，不包含已有摄像头和Observer。按本轮CPU-ms粗算各跑10次/秒约18.5%/15.4%单核、合计33.9%，这是调度预算估算，未实测双模型连续视频共存。保持5Hz可减半；不得以单图连续循环CPU%误称固定5/10Hz占用。

**关键纠正：** `rknn_run` 不应写成纯NPU时间。RetinaFace逐层信息明确5个CPU Transpose、部分CPU Reshape和FLOAT16 CPU `exSoftmax13`；诊断单次算子表CPU3.820ms、NPU8.786ms，其中Transpose2.118ms、Softmax1.252ms。该诊断有额外开销，与正常100次统计不直接相减，也不能据它将全部CPU-run时间归因某个算子。YOLO主要算子在NPU，OutputOperator显示CPU，诊断单次3.010ms；CAPI读取2,142,000字节INT8输出及布局/缓存处理值得优先优化，但尚未独立分解每种拷贝/转换，不能宣称8.93ms全是拷贝。

运行基线（未运行检测、8秒）：FFmpeg44.50%单核，Observer43.25%，v4l2-ctl2.62%，三进程合计90.37%，约占四核理论总能力22.6%；其它系统开销另计。短时采集器3.37%不计入服务。另一次6秒线程采样：servo-owner30.17%、imu-reader6.17%、Tokio线程合计5.83%，故主服务占用不能全归摄像头。摄像头实出10.125fps；CPU当前及max均1.104GHz，DDR1.056GHz，NPU900MHz，SoC85℃。无强行锁频/停温控；高温和调度可影响不同轮次，不能把早期46ms和本次49.7ms直接归因回归。

现有链路：IMX219/ISP → 640×360 NV12 → v4l2 mmap/pipe → FFmpeg按30fps读入、fps滤镜选10fps → NV12/RGB转换、白平衡gamma LUT → 软件MJPEG编码 → Rust发布JPEG → 网络/浏览器解码显示并旋转。RGA目前只在独立检测程序缩放，不在FFmpeg相机链路。10fps代表帧间隔100ms，不代表纯传输延迟；浏览器缓存、网络、传感器曝光至显示延迟本次未打同步时间戳，未测出端到端延迟。独立检测测的是已读入并旋转的图，JPEG解码、旋转、图像输出都不在上述循环表内。

补充FFmpeg隔离累加试验：用同一张实拍转换NV12循环文件，每组100输出帧（原摄像头保持运行），drop-only/RGB转换/加LUT/加MJPEG的CPU-ms/输出帧分别20.218/40.375/46.340/107.750。它包含文件输入、滤镜/编码/框架/启动开销且额外增加系统负载，不等于线上单项精确耗时，不可将最后107.75ms替代线上44.5%占用。只能作为格式转换、JPEG编码值得进一步采样的证据，不能把累加差值当稳定独立算子时间。

优化顺序建议：①检测直接消费原NV12/共享帧，RGA一次做旋转/缩放/颜色转换，避免JPEG回读及多次映射；②YOLO研究原生输出布局/缓冲复用，保留坐标/分数回归对照；③RetinaFace重导出移除/调整CPU Transpose、Reshape、Softmax并重新量化/比对，不能只修改want_float就声称解决；④相机链路评估硬件颜色转换和编码支持；⑤处理散热后重测。当前不擅改舵机/IMU采样率，NMS余项很小不优先重写。
